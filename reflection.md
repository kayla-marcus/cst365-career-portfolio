## Reflection

Building the Meridian Bank SRE Incident Dashboard helped me connect course concepts to a working application and better understand how reliability practices support real engineering decisions. Instead of treating observability, error budgets, and DORA metrics as separate topics, I wanted to show how they work together during an incident. For example, connecting failed deployments to incidents and providing recommendations based on error budget status helps demonstrate how reliability data can guide decisions about whether to continue releasing features or focus on fixing existing issues.

One of the biggest takeaways from this project was the importance of making data accurate and useful. Using Claude, I separated the data, calculation logic, and interface, then wrote 15 automated tests to verify calculations, handle overlapping incidents, and keep the displayed numbers consistent. I also applied observability concepts through metrics, structured logs, alert thresholds, and detection gaps. The blameless postmortem feature reinforces the importance of understanding what contributed to an incident rather than focusing on who caused it. These areas connect most directly to CLO4 and CLO5, while the project only partially addresses CLO1 and CLO6 and does not demonstrate CLO2 or CLO3.

My next step would be to add a GitHub Actions workflow that runs the tests, verifies that the generated `index.html` matches the source files, checks for exposed secrets, and deploys to GitHub Pages only when the checks pass. This would be a practical way to apply CI/CD concepts without adding infrastructure that the application does not need. From there, I would focus on connecting the dashboard to live observability data and deployment events, followed by adding persistence and distributed trace navigation. These improvements would address the current limitations while allowing me to build on the existing project and demonstrate more of the course concepts through implementation.
